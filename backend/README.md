# Blood Connection API

An initiative by Bindubashini Boys’ 2015 & Friends

Python 3.11+ and SQLite are sufficient for the local service. Start from the repository root in PowerShell:

```powershell
python -m venv backend/.venv
backend/.venv/Scripts/python -m pip install -r backend/requirements.txt
$env:DEMO_MODE = '1'
backend/.venv/Scripts/python -m backend
```

The default listener is `http://127.0.0.1:8000`. `/` redirects to the administration website at `/admin/`; regular members use the native app. `/api/v1/health` reports local/demo/calling capabilities, and `/openapi.json` contains the machine-readable endpoint schema. Connect Android with `adb reverse tcp:8000 tcp:8000`; no LAN exposure is needed. The launcher, request client address, and Host header all restrict demo mode to loopback. Demo bearer tokens (`demo-seeker`, `demo-donor`, `demo-admin`) are deliberately public local fixtures, never production credentials.

Run the integration tests:

```powershell
backend/.venv/Scripts/python -m unittest backend.test_app -v
```

Tests create temporary databases and exercise profile validation, BMI, the 39 km boundary, exact group filtering, private search projections, object authorization, blocks, reviewed bans, append-only audit, travel, calendar-month cooldowns, account export/deletion, provider enforcement, secret-key rejection, request limits, demo isolation, call acceptance, media retries and expiry. They also test simultaneous request acceptance, photo sanitization/access revocation, personalized thanks, inbox pagination, encrypted push/decryption, retries, cooldown suppression, device removal, allowed relay origins and generic APNs/Apple Watch notification payloads. Provider HTTP calls are mocked in these unit/integration checks; this does not establish real OAuth, audio or Apple delivery interoperability.

With the local ntfy relay running on port 8090, `backend/.venv/Scripts/python -m backend.check_push` uses disposable accounts and proves the real request → outbox → relay → client decryption path. It does not claim OS-level device delivery; test that separately on a physical device.

## Storage and isolation

`DATA_DIR` defaults to `backend/data`. `registry.sqlite3` stores opaque account IDs, active country, voluntary availability, cooldown, bans/deletion tombstones, donation dates, relationship blocks, moderation audit, private device endpoints and media-revocation work. It also reserves accepted donor/requester pairs globally to prevent multiple simultaneous matches. Each ISO country gets a separate `XX.sqlite3` file with profiles, private photos, conversations, messages, reports, requests/invitations, event inboxes, push outboxes and call invitations. Country names come from the ISO dataset in `pycountry`; production only exposes `ENABLED_COUNTRIES`.

This is real country-file separation on one development machine. It is **not geographic data residency**. Multi-country public launch requires region-local databases, a minimal authenticated global registry, per-region encryption/backups and a reviewed cross-border transfer policy. Do not run several API hosts against independent copies of these SQLite files. Rate limits are process-local; use a shared rate limiter before multiple workers or replicas.

`POST /api/v1/location` accepts `{country, city, latitude, longitude, mode}` with mode `automatic` or `manual`. It works before health-profile completion, updates the full location together, and returns the owner profile including `location_mode`. The account preference defaults to automatic through an additive, transactional migration. Native clients must obtain permission and the user's opt-in before automatic location updates; the server does not infer consent from the mode string or collect background locations itself. Geographic input is client-supplied, not attested or proof that the coordinates are inside the named country. Reverse geocoding happens on the native client.

An attached SQLite transaction moves the profile to the destination and deletes the origin profile. Messages/reports remain in their original country. Cooldown, voluntary offline preference, blocks and bans remain global. A cold `GET /me` recovers an existing account's active country even when the header is absent or stale; existing-account `/location` also resolves the saved source country. A new member with no country header gets 409 asking them to detect/select a location, without creating a default Bangladesh account. A new member supplies their detected or manually selected country in `X-Country` for the initial `/location` call. A new administrator may bootstrap with no header using the first enabled country. Other routes require the active country, except admin routes can select another enabled country.

Identical location readings do not rewrite storage or consume the movement budget. Changed readings allow 60 updates/hour/account and cross-country moves allow 10/hour. `/travel` remains a consent-based compatibility endpoint for completed profiles and selects manual mode. `/me` profile updates must carry the latest saved city and coordinates: stale or missing location fields return 409 in either mode rather than overwrite a newer location. Change location through `/location` first, then save the profile returned by that call.

## Sign-in and roles

Set `DEMO_MODE=0`, `SUPABASE_URL` to an HTTPS project origin, and `SUPABASE_ANON_KEY` to its **public publishable/anon key**. Secret/service-role key formats are rejected because `/api/v1/auth/config` deliberately exposes public client configuration to the browser. Enable only Google, Apple and Facebook in Supabase and configure their redirect allowlists. Each bearer token is verified with Supabase's `/auth/v1/user`; server-controlled `app_metadata.provider` must be one of those three. Provider admin configuration must prohibit password/email login and unapproved account linking. Tokens and credentials are never persisted by the API.

`ADMIN_USER_IDS` is a comma-separated list of verified Supabase user UUIDs. User-editable metadata, profile request fields and frontend state cannot grant administrator privileges. Configure MFA for administrator accounts before public use; the current API does not enforce an MFA assurance-level claim. A lifetime ban applies to that account identity worldwide. Detecting the same human opening a new social account requires a separate abuse prevention/appeals process; the app does not collect identity documents or claim to solve that problem.

The API rejects authenticated non-administrators on browser requests carrying `Origin` or any `Sec-Fetch-*` header, including `/me`. Native members and native/browser administrators retain their role-appropriate access. A spoofable `X-Client` claim never grants an exception. This is a browser-product gate, **not proof of a genuine native app**: a custom HTTP client can omit these headers. Enforcing trusted-app-only clients requires server-verified Android Play Integrity and Apple App Attest (including replay protection) before public rollout; neither device attestation nor GPS attestation is implemented here.

## Privacy and moderation

Search returns alias, group, city and 5 km distance bands capped at 39 km. It never returns coordinates, phone numbers, email addresses, height, weight or BMI. Searches must start within 1 km of the saved location and are limited to 30/minute per account. A determined user can still infer location through repeated nearby searches, location updates or multiple accounts. Add abuse monitoring and stronger location blurring before public launch; precise stored coordinates need protected/encrypted storage. These data files are unencrypted at the application layer: use OS disk encryption and restrict filesystem access locally.

Profiles and messages are authenticated. Messages are stored as plaintext in the regional database; the service is **not end-to-end encrypted**. Use HTTPS in production and encrypted backups. A participant can report a conversation; the service snapshots its latest 20 messages for review. Only admins can view report evidence. A confirmed money request requires a review note and creates a permanent global ban with append-only audit. A report alone never bans a donor. Blocks immediately stop future contact and new media credentials.

Account deletion immediately revokes app access using a tombstone, removes registered push endpoints and donation records, then removes profiles/photos/owned inbox content and replaces the owner's normal message content with `[Message removed]` across local country files. It closes active matches. It retains report evidence, moderation audit and the identity tombstone for enforcement. It does not delete the upstream Supabase auth identity. No retention expiry is invented here: agree and implement a lawful retention, backup-erasure and appeals policy before public launch. A durable deletion job retries interrupted regional scrubbing every 15 seconds; `erasure_pending` in the deletion response indicates whether erasure remains queued.

## Donation requests and private photos

`POST /api/v1/requests` accepts `{blood_type, radius_km, destination_name, destination_latitude, destination_longitude, donor_ids?}`. The optional ID list selects up to 50 donors; without it, the nearest 50 eligible donors are invited. The server checks exact blood group, availability, three-month cooldown, blocks, current country, completed profile and a radius of 1–39 km around the seeker's saved location. A selected donor who is no longer eligible causes 409 so the user can refresh. The destination is an explicitly chosen hospital/place: **never a donor's saved coordinates**. The server validates numeric bounds, not that the typed place is a real hospital.

`GET /requests` and `GET /requests/{id}` return only owned or invited requests. Requests start open and expire after 24 hours unless accepted. `POST /requests/{id}/accept` lets an invited, still-eligible donor accept. An immediate SQLite transaction selects exactly one winner, creates/reuses the private conversation, and reserves the donor/requester globally. Repeating the winning acceptance is idempotent. A second donor gets 409. The requester and accepted donor then receive the meeting destination and the counterpart's photo-access flag. Other invitees receive neither the counterpart nor destination coordinates.

`POST /requests/{id}/decline` declines an open invitation. `/cancel` closes an open request for its owner or an accepted request for either participant. `/complete` closes an accepted request for either participant; this does not fabricate a clinical donation or change cooldown. Donors log actual donations separately. Closing, blocking, banning, deleting or moving either matched account to a different country revokes photo/map access and releases the match reservation. Historical coordination messages remain subject to their normal participant checks.

`PUT /me/photo` accepts raw `image/jpeg` or `image/png` bytes up to 5 MiB and 12 megapixels, and rejects animations. Pillow applies orientation, fits the image inside 512×512, and encodes fresh JPEG pixels with metadata stripped. The source file is never stored. `DELETE /me/photo` removes it; `GET /me` includes `has_photo`. `GET /profiles/{user_id}/photo` returns authenticated JPEG bytes with `no-store` only to the owner or a currently accepted counterpart. Admin role alone does not bypass this permission. Donor discovery never includes photo URLs or photo flags. Photos reside in a private regional BLOB, move atomically with their owner during travel and are included in the owner's export; there are no public image URLs. Recipients can still capture a photo already displayed, so revocation cannot erase their screenshots.

## Background notifications

Request invitations, acceptance, closing and personalized thank-you messages create a durable regional event inbox and per-device outbox **in the same transaction** as the request change. After one donor accepts, other still-available invited donors receive personalized thanks. Their thanks remain available after request completion. `GET /events` defaults to the latest 100 eligible events, newest first; `GET /events?after=N` streams eligible events ascending after a country-local integer ID and returns `next_after`. Suppressed rows do not block later entries. `POST /events/{id}/read` marks only the owner's event read.

`POST /devices` accepts `{provider:'unifiedpush'|'apns', token, pub_key?, auth?}` and returns `{id, provider, status:'registered'}`. For UnifiedPush, the token is the distributor endpoint and the two key fields are base64url P-256 and 16-byte auth keys. For APNs, the token is device-token hex. This uses the existing authenticated account; there is no separate notification registration/login. Tokens are never listed publicly, never transferable to another account without removal, and limited to five per account. `DELETE /devices` with `{token}` removes only that user's matching registration. The native app must cancel/invalidate stale registration callbacks on sign-out before deleting the endpoint; a server cannot identify a late callback using the same still-valid bearer token as a different session without an explicit session protocol.

Android uses encrypted UnifiedPush deliveries. `PUSH_ALLOWED_ORIGINS` is an explicit origin allowlist; production requires HTTPS. Demo may allow loopback HTTP, e.g. `http://127.0.0.1:8090`. The worker rechecks the origin at delivery, does not follow redirects, validates encryption keys and uses `aes128gcm` payload encryption. `X-UnifiedPush: 1` enables ntfy's binary UnifiedPush path. Use an authenticated, controlled distributor in production; random public topic names alone do not establish access control. See [ntfy UnifiedPush publishing](https://docs.ntfy.sh/publish/) and [pywebpush encryption](https://github.com/web-push-libs/pywebpush).

iOS uses APNs directly over HTTP/2, configured by `APNS_KEY_PATH`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_TOPIC`, and `APNS_SANDBOX`. The ES256 provider key stays outside source control. No Firebase SDK/service is used. The alert is always “You have a private update. Open the app to view it.” with the `PRIVATE_UPDATE` category for the native app's safe watch action. Neither provider receives personalized names, blood group, photo or meeting location; transport payloads contain only event/request IDs, country and kind. Personalized content is fetched from the authenticated inbox. See [Apple's APNs request documentation](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns).

The 15-second worker leases outbox entries, checks bans, deletion, current country, blocks, request state and donor availability/cooldown again before delivery, and retries transient failures with backoff (at most 12 attempts and 24 hours). Permanent invalid endpoints are removed; a missing APNs configuration is never reported as successful delivery. A successful provider response means accepted by the provider, **not proven display on a phone**. Delivery is at least once: deduplicate using country/event ID. Disabled/cooling-down donors do not receive blood-request/thanks alerts. An alert already in transit or accepted by the OS cannot be recalled when eligibility changes; the alert is generic and content fetch is re-authorized. Native permission, background restrictions and distributor setup must be tested on devices.

## Availability and calls

Availability is derived at read time: voluntary opt-in, no ban/deletion, and the three-calendar-month cooldown deadline has passed. `POST /donations` accepts e.g. `{"donated_at":"2026-11-15","utc_offset_minutes":660}`. The optional integer offset is bounded to -720..840 and defaults to UTC for older clients. Future dates are checked against today at that supplied offset, so a legitimate Sydney morning donation is not rejected just because UTC is still yesterday. End-of-month dates clamp to the target month; the deadline is midnight of that clamped date at the recorded fixed offset, stored as `eligible_after_utc`. This uses the recorded offset, not an IANA timezone or future daylight-saving prediction. `eligible_after` remains a compatible display date. Existing records without an instant retain their previous UTC-date policy. New/backdated logs or changed offsets cannot shorten the existing absolute deadline, and travel cannot reset it. No scheduler is needed for reappearance, and a voluntary offline preference stays offline after the pause. This is an app calendar-day contact rule, **not clinical eligibility** or a precise timestamp of the donation. A licensed donation service determines donation suitability and any longer country-specific deferral.

Donation-request updates support background delivery as described above. Chat messages and live call invitations still use foreground polling; they do not yet have background call/VoIP push integration. `GET /calls` suppresses invitations while the recipient is unavailable or on cooldown. A caller receives no media token until the recipient accepts.

Configure `LIVEKIT_URL` (secure `wss://` origin), `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` for actual audio. Unconfigured calls return 503 with a clear explanation. The API issues room-scoped audio-only tokens lasting at most five minutes. Ringing invitations expire after 60 seconds; accepted calls expire after one hour so a crashed client cannot leave the conversation busy forever. Clients should poll call status and disconnect on ended/forbidden responses.

End, block, ban, travel and deletion close call state and queue durable media revocation. A 15-second worker removes both participants and deletes the room using LiveKit's authenticated service API; failures remain queued for retry. Ending a call also attempts cleanup immediately. LiveKit Cloud's RemoveParticipant revokes the participant's current token. A self-hosted LiveKit server may permit an issued token to reconnect until its five-minute expiry, even after room deletion. Existing media can continue during a provider outage; frontend disconnect and server retries mitigate but cannot eliminate that outage window. See the [LiveKit room service API](https://docs.livekit.io/reference/other/roomservice-api/).

## Before a public deployment

Use HTTPS, explicit CORS origins, a 32 KB proxy body limit (5 MiB only for the authenticated photo route), encrypted storage/backups, restricted server credentials, regional deployment/transfer policies, shared abuse limits, monitoring, tested backup restoration, MFA enforcement and monitored deletion/revocation/outbox workers. Configure and test real OAuth, background delivery and two-party audio on devices. Verify emergency/clinical language, consent and privacy terms for each launched country. The local implementation intentionally makes no claim that all countries are deployed, legal requirements have been reviewed, or live social-provider/Apple push setup has been completed.
