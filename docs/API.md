# Blood Connection API contract

Base URL `/api/v1`. JSON except bounded binary profile-photo and report-evidence uploads/downloads. All protected requests use `Authorization: Bearer <token>` and `X-Country: <ISO alpha-2>` once a region is known (BD only for fictional local fixtures). `GET /me` recovers an existing account's country without a header; new members must resolve their country first. Production tokens are Supabase access tokens verified server-side; only Google, Apple and Facebook identities accepted. Local demo mode is explicitly enabled with `DEMO_MODE=1`, bound to loopback only. Clients use `demo-donor`, `demo-seeker`, `demo-admin` tokens solely in demo builds. Never deploy demo mode. Browser member requests are rejected; administrators may use mobile and web. Header checks are not device attestation.

All timestamps are UTC ISO 8601. IDs are strings. Errors return `{"detail":"human readable error"}`. Lists use `{"items": [...]}`. No phone numbers, emails, height, weight or exact coordinates in donor search responses.

* `GET /health` -> `{status, demo, calling_enabled}` (no authentication).
* `GET /auth/config` -> `{supabase_url,supabase_anon_key}` public provider configuration for the admin app. Secret/service-role keys must be rejected during configuration.
* `GET /countries` -> `{items:[{code,name}]}`. ISO countries provisioned lazily in local mode; production must configure enabled countries.
* `GET /me` -> `{id,display_name,blood_type,height_cm,weight_kg,bmi,country,city,latitude,longitude,available,eligible_after,is_available,role,location_mode}`. Role set by server only. This read recovers the account's active country even when the client sends a stale country header after travel; other regional endpoints remain strict.
* `PUT /me` body `{display_name,blood_type,height_cm,weight_kg,city,latitude,longitude,available}`. Country comes from header. Returns profile. Bounds: name 2–60, height 100–250 cm, weight 30–300 kg, lat -90..90, lng -180..180, valid ABO/Rh only. Initial profile may be incomplete; searching/contact requires completed profile.
  Location fields must match the current server profile; stale fields return 409. Change country/area through `/location` first, then use its returned profile when saving measurements. This prevents an old edit form from reversing a fresh automatic location update.
* `POST /location` body `{country,city,latitude,longitude,mode:"automatic"|"manual"}` -> owner profile. Resolves the source region from the account, atomically updates the entire location or transfers its profile, and supports incomplete new profiles. Preserves global recovery dates, availability and enforcement. Mode is durable; duplicate readings do not rewrite data. Requires a resolved country header to create a first account. GPS/area resolution and consent are handled by the native client; these inputs are not a claim of device attestation.
* `POST /travel` body `{country,city,latitude,longitude,consent:true}` -> profile. Moves active discovery region; previous country profile is removed. Global cooldown, preferences and ban persist. Destination must be enabled. Does not copy messages across borders.
* `GET /donors?blood_type=O%2B&radius_km=10&latitude=23.81&longitude=90.41` -> `{items:[{id,display_name,blood_type,city,distance_band,map_area:{id,latitude,longitude}}]}`. Exact blood group only, radius 1–39 enforced server-side against private coordinates. Distance bands are `Within 5 km`, `Within 10 km`, etc. Results restricted to active country and currently available donors; excludes self. No medical compatibility inference. `map_area` is a fixed coarse geographic cell center, **not the donor's location**; group map markers by its ID. See the area contract below.
* `GET /donations` -> `{items:[{id,donated_at,facility_name,location_name,country,request_id,created_at,confirmed_by_role}]}`. Full history is donor-owner-only across travel. `confirmed_by_role` identifies donor or seeker confirmation; legacy place details can be null.
* `POST /donations` body `{donated_at,facility_name,location_name,country,utc_offset_minutes?,request_id?,idempotency_key?}`. Required place labels are trimmed 2–160 chars; country is an ISO code. Unlinked entries target the caller. Linked entries require membership in the completed donor/seeker pair and always target its actual donor. The first Yes atomically records one donation, marks the receipt recorded and extends the donor cooldown if needed. Returns the CALLER profile, never another person's private profile. Same actor/key/body retries are safe; changed details with a committed key return 409. Request-linked concurrent confirmations cannot create a second row. Dates cannot be future in the bounded offset (-720..840 minutes); the three-calendar-month UTC deadline never shortens an existing pause.
  `idempotency_key` is an optional trimmed string of 16–128 characters, scoped to the submitting account. A retry with the same key and normalized date/facility/location/country/request reference returns the current profile without a second record. Reusing that key with changed recorded fields returns 409 and requires reviewing history before starting another entry. A changed UTC offset does not rewrite a committed entry's original cooldown. The mobile recorder generates one random key per entry and reuses it for retries. Keys are not returned by history/export. Clients that omit the key retain legacy manual-submission behavior, so use a stable key for retry safety.
* `GET /donation-confirmations` -> `{items:[{request_id,facility_name,location_name,country,created_at,is_donor,donor_name}]}`. Pending reminders for the authenticated matched participant, across travel. Meeting name/country are editable suggestions, locality stays explicit. No photo, precise destination or unrelated donor history is included.
* `POST /donation-confirmations/{request_id}/dismiss` -> `{status:"dismissed"}`. Only that participant's reminder is dismissed; the other participant can still confirm Yes. No donation/cooldown is created. Unrelated receipts return 404; an already recorded receipt returns 409.
* `GET /conversations` -> `{items:[{id,peer_id,peer_name,blood_type,last_message,updated_at,is_blocked}]}`. Blocking stops new messages/calls, but preserves participant access needed to report misconduct.
* `POST /conversations` body `{donor_id}` -> `{id,peer_id,peer_name,blood_type}`. Donor must be discoverable within 39 km from caller's saved location; no self contact. Reuse existing conversation.
* `GET /conversations/{id}/messages` -> `{items:[{id,sender_id,body,created_at}]}`. Participant authorization mandatory.
* `POST /conversations/{id}/messages` body `{body}` -> message. 1–2000 chars. Block banned users and blocked relationships. Do not send notifications to donors in cooldown.
* `POST /reports` body `{request_id?|conversation_id?,reason,details,idempotency_key?}` -> `{id,status}`. Exactly one relationship reference is required. Reason is `money_request`, `harassment`, `misleading_information`, `no_show` or `other`; details 5–2000 chars. Conversation members or the matched request pair can report, including after closure/block. The target is inferred server-side and recent conversation evidence is snapshotted. Stable actor/key/body retries return the same report; changed details with a committed key return 409.
* `GET /reports` -> `{items:[{id,country,request_id,reason,details,status,outcome,submitted_at,reviewed_at,outcome_explanation,attachments}]}`. Latest 100 reports submitted by the caller across existing country databases, newest first. `status` is `pending` or `reviewed`; `outcome` is null, `banned` or `dismissed`. Pending outcomes/explanations are null. Reviewed reports contain a fixed safe explanation, never the internal review note, audit record or conversation-evidence snapshot. `reviewed_at` is nullable for legacy reviews whose time was not recorded. Each attachment is `{id,content_type:"image/jpeg",created_at}`.
* `GET /reports/{id}?country=BD` -> the same owner-only report object. The optional query selects its stored region; keep `X-Country` set to the caller's active country. Omit the query to read the active region. A guessed report ID, accused participant or administrator using this owner route does not bypass reporter ownership. Unknown stored countries/reports return 404; reads never move a profile or create a regional database.
* `POST /reports/{id}/evidence` raw `image/jpeg` or `image/png` -> `{id,content_type:"image/jpeg",created_at}`. Reporter-only, pending reports, maximum three attachments and 5 MiB input each. Image bytes/dimensions are validated; output is EXIF-free JPEG with longest edge <=2048px. Identical source retries return the existing attachment. Reviewed evidence cannot be mutated.
* `GET /reports/{id}/evidence/{attachment_id}?country=BD` returns JPEG bytes to its reporter only, with `Cache-Control:no-store`. The optional stored-country query supports access after travel, just like owner report detail.
* `GET /admin/reports/{id}/evidence/{attachment_id}` returns the selected region's JPEG to authenticated administrators, excluding an accused administrator. No public URL or token in a URL is needed.
* `POST /blocks` body `{user_id}` -> `{status:"blocked"}`. Only conversation peers can be blocked.
* `GET /calls` -> `{items:[{id,conversation_id,caller_id,caller_name,status}]}` pending invitations for current user.
* `POST /conversations/{id}/calls` -> `{id,status:"ringing"}`. `503` if LiveKit unconfigured. Never pretend a call connected.
* `POST /calls/{id}/accept` -> `{id,url,token}` only callee. `GET /calls/{id}` -> `{id,status,url?,token?}` caller gets credentials only after acceptance. Short-lived room-scoped tokens. `POST /calls/{id}/end` -> `{status:"ended"}`. Blocked/banned users denied.
* `GET /admin/reports` -> reports with reason/details/status, `reviewed_at`, recent-message `evidence`, and `attachments:[{id,content_type,created_at}]`. Authenticated global administrators select a region; no per-admin country-assignment map exists. Accused administrators cannot inspect their own allegation. Attachment bytes require a separate authenticated request.
* `POST /admin/reports/{id}/resolve` body `{decision:"ban"|"dismiss",note}` -> `{status:"banned"|"dismissed"}`. Ban decision only for confirmed money requests; permanent global ban, immutable audit trail. The internal note is 5–2000 characters. Resolution time, status, any ban, audit record, one reporter inbox event and its per-device outbox entries commit atomically. A repeated/concurrent resolution returns 409 without a second event. Both decisions notify the reporter; the accused does not receive that report's private outcome alert. Other reports can be dismissed; block protects participants.
* `GET /admin/summary` -> `{pending_reports,banned_accounts,active_donors,country}`.
* `GET /me/export` -> own account data and regional records.
* `DELETE /me` -> `{status:"deleted",erasure_pending}`. Minimize profile and messages; retain minimal ban/audit evidence according to documented policy. Account cannot use existing tokens after deletion. Durable background retries complete interrupted regional scrubbing.

## Approximate donor areas

Every donor result includes `map_area: {id, latitude, longitude}`. The current `area-v1-<row>-<column>` identifier describes a global, query-independent grid. Latitude rows are 0.05° (about 5.56 km); longitude cells are sized from the row's poleward edge using a 5.1 km arc-width target, providing a margin above approximately 5 km across the narrowest edge. Each top/bottom 0.05° polar cap is one area, centered at ±90° latitude and 0° longitude. The first longitude cell straddles the antimeridian, and +180°/-180° inputs have identical results. All members within one cell get the same ID and coordinates, independent of requesting user, search origin or radius. There is no random jitter to average away.

Treat these as approximate **area centroids**, cluster by `map_area.id`, and never label them as a person's pin or use them for navigation to a donor. A center can lie outside a small selected radius, across a country border, or over water; the actual result still passed private exact-radius and country filtering. Clamp only the renderer's map projection if it cannot display poles. The map area does not change accepted-request destination sharing, which remains a separately chosen meeting point. Coarse display does not eliminate inference from repeated exact-radius searches or observations over time.

## Consent, photos and donation requests

`GET /me` also returns `has_photo` and nullable `eligible_after_utc`. Prefer the precise timestamp for cooldown decisions; legacy date-only records use UTC midnight. A photo is never included in donor discovery or exposed through a reusable public URL.

| Method/path | Input and behavior |
| --- | --- |
| `PUT /me/photo` | Raw JPEG/PNG, matching content type, maximum 5 MiB. Decode at most 12 megapixels, orient/resize to 512px, re-encode without metadata. Returns `{has_photo:true}`. |
| `DELETE /me/photo` | Removes the owner's private photo. |
| `GET /profiles/{id}/photo` | Authenticated JPEG, `Cache-Control: no-store`. Owner or currently accepted counterpart only; other callers receive 404. |
| `POST /requests` | `{blood_type,radius_km,destination_name,destination_latitude,destination_longitude,donor_ids?}`. Rechecks eligible selected donors in the current country within at most 39 km. Stores a deliberately shared hospital/public meeting point, never a donor GPS point. One active request/match per participant. |
| `GET /requests` | Current member's requests/invitations, with private destination and counterpart fields projected according to acceptance. |
| `GET /requests/{id}` | Same participant authorization/projection as the list. Nonparticipants receive 404. |
| `POST /requests/{id}/accept` | An invited eligible donor accepts atomically. Exactly one winner; repeat by that winner is idempotent. Returns accepted request with a private conversation. Other invitations close and receive personalized thanks. |
| `POST /requests/{id}/decline` | Decline one's open invitation. |
| `POST /requests/{id}/cancel` | Requester or accepted donor closes the request and revokes future photo/meeting access. |
| `POST /requests/{id}/complete` | Either accepted participant closes coordination and creates the shared completion reminder. Completion itself is not a donation; either matched person can subsequently submit the actual donor's record. |
| `GET /events` | Latest 100 eligible owner events across existing regions. Each item includes `{id,country,kind,title,body,request_id,report_id,report_country,created_at,read}`; report-review events have `request_id:null`. Donation-event report fields are null. See cursor/target rules below. |
| `POST /events/{id}/read?country=BD` | Marks only the current member's event read in its stored country. IDs are regional, so pass the event's `country` after travel; omission selects the active region. |
| `POST /devices` | `{provider:"unifiedpush"|"apns",token,pub_key?,auth?}`. UnifiedPush requires the P-256 public key/auth secret and an allowed endpoint origin. Returns `{id,provider,status:"registered"}`. Tokens are not exposed by list/export routes. |
| `DELETE /devices` | `{token}` removes only the current member's registration. |

Open requests expire after 24 hours. Bans, deletion, blocking and travel invalidate applicable matches. An accepted counterpart gains photo access only while the relationship remains valid; completing/cancelling removes it. A request's original owner can still read their own meeting data. See [notification operation](NOTIFICATIONS.md) for real delivery setup and limits.

The default event inbox sorts across countries by newest creation time and returns at most 100 entries. `GET /events?country=BD` restricts that view to a stored region. `GET /events?country=BD&after=123` instead streams up to 100 eligible events in ascending regional ID order; if `country` is omitted with `after`, it uses the active region. Responses include `next_after` and `cursor_country`. A numeric cursor is valid only for that country, not for the combined inbox; default combined responses report the active region's cursor. Older ineligible events are scanned past so they cannot hide newer eligible updates.

`report_reviewed` events point to `report_id` and `report_country`. Their authorization verifies that the recipient submitted that reviewed report. They remain eligible after travel, donor opt-out/cooldown, or blocking the accused; banned/deleted recipients are still excluded. Donation events retain their existing country, relationship, request-state and donor-eligibility rules. No historical review events or review timestamps are invented during migration. Delivery is at least once with client `(country,event_id)` deduplication; one committed outbox entry does not guarantee exactly-once network delivery.

Donation history is global donor-owned data; confirmation receipts are shared only with the matched seeker/donor. Matched request responses include `can_report`, `donation_recorded` and a limited `donation_summary` with date/place/confirmer role. This does not reopen photo access or expose unrelated history. Existing receipts can recover their matched requester during migration, without manufacturing receipts for every historic completed request. See [donation status and history](DONATIONS.md).

Demo fixtures: donor (Nadia, O+, Dhaka, 23.8103/90.4125), seeker (Rafi, B+, nearby), additional fictional donors for search and one fictional money-request report. Demo mobile defaults to seeker. Admin uses demo-admin. Never label sample data as verified people.
